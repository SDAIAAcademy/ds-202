The decision rule

Decide per line: valid UTF-8 is UTF-8; what is not is the legacy code page

def decode(b: bytes):
    try:
        return b.decode("utf-8"), "utf-8"
    except UnicodeDecodeError:
        return b.decode("cp1256"), "cp1256"
  • Arabic in Windows-1256 is almost never valid UTF-8, so the test is safe in this direction
  • Return the encoding with the text and count it
  • The count has a shape: all 5,458 lines are from two branches. A scatter over all branches would mean the rule is wrong

The order matters: try the strict encoding first. UTF-8 has structure (lead and continuation bytes) that random legacy bytes almost never satisfy; cp1256 accepts anything. Lines with only Latin letters and digits are the same bytes in both and decode as UTF-8, which is harmless. Sources: Python codecs documentation.

  • So the function is safe on all 40,000 names, and changes 2,732, every one at B06

The tell is the repeated ط and ظ: the bytes D8 and D9 that begin every Arabic letter in UTF-8. Show head_name_raw beside head_name for three rows of B06. The check that all repaired rows are at one branch is the evidence that the rule did what it claims.

The habit of the day

A repair that is not counted cannot be checked, repeated or reversed

A rule

Written as code, applied to every row, never by hand to a few.

A count

One line per rule in a log: how many rows it changed, and where.

The original

Kept beside the repaired value, so a reviewer can disagree.

The same three in every lab today: a repair log, a join log, a threshold table, a change log.

These four files are sections of the quality report on Day 4, and of the capstone README: the rubric gives 25 points to joins and reconciliation and 25 to cleaning and validation, and the evidence for both is counts per step.

Checkpoint

Which loader do you trust?

A file was appended from several systems. Four loaders are proposed. Which one do you run?

Read it all as Windows-1256: it raises no error
Read it as UTF-8 and replace undecodable bytes with a mark
Let a detection library pick the encoding of the file
Decode line by line, UTF-8 first, and count the lines of each encoding
Why. The file has no single encoding, so the decision has to be made where the encoding changes, per line, and the count per encoding is the check on the decision.

Answer: D. Option B is the common one in practice (errors="replace") and destroys 5,458 names for good. A detection library answers a different question: the most likely single encoding.

Session 2

Keys and cardinality

  • Repair mistyped keys by stated rules
  • Test many-to-one before joining
  • Reconcile rows in with rows out plus rows set aside
02
Many handouts, one household

A join can lose rows, add rows, and report neither

Lost

A key typed by hand does not match. In an inner join the handout disappears.

Added

A household that is in the register twice gets every handout twice.

Unnoticed

The result is a table of plausible size. Nothing compares it with what went in.

The remedy has three parts, in this order: repair keys by rule, test the cardinality, count rows at every step.

FN-104 showed fan-out in SQL and validate= in pandas. Outcome LO3 asks for more: a join log of row counts per step and set-aside rows with reasons. That log is 25 of the 100 points of the capstone rubric.

Session 3

Matching without a clean key

  • Block and score candidate pairs
  • Measure false matches and missed matches on labelled pairs
  • Choose a threshold and state its cost
  • Build a master record field by field from records that disagree
03
The problem

300 handouts were written on paper, with a name and no id

  • A satellite point of B04 and B05 in Ramadan: a name, a district, a phone for seven in ten
  • 4,937 active households of the two branches to search
  • Staff labelled 848 candidate pairs by hand: 255 true, 593 not

Two errors, two prices

Missed match: a handout stays uncounted, and you can see it.
False match: one family is credited with another's parcels, and it looks like a success.

The labelled pairs are the most valuable file of the session: without them a threshold is an opinion. In real work, labelling a few hundred pairs is half a day for two people and is always worth it. The 593 non-matches were chosen to be hard: same first name and family name, another person.

Three steps

Block, score, decide

1 · Blockcompare only pairs that agree on a reliable field: the district
→
2 · Scorehow alike are the two name keys, from 0 to 100
→
3 · Decideaccept, reject, or send to a person

Blocking: 311,703 candidate pairs instead of 1,481,100, and all 255 true pairs survive it.

A true pair that disagrees on the blocking field is never compared: check that on the labelled pairs.The score in the lab is token_sort_ratio from RapidFuzz: sort the words, then an edit-based similarity. It is one of many; the method of measuring does not depend on the choice. Sources: RapidFuzz documentation.

Measured on the 848 labelled pairs

From the Lab 2.3 run. The four false matches at 95 are pairs with identical name keys: two people called the same. No amount of tuning the name score can separate them. Ask: which of these three would you run on the register? None is acceptable, which is the point of the next slide.

The decision has three outcomes

Accept, reject, or ask a person

Accept automatically

The rule that showed no false match on labelled pairs. 172 of 300 walk-ins.

Review

Likely names without a phone, or several candidates. A person decides, and the decision is recorded.

Leave unmatched

45 walk-ins are new households. An unmatched record is an honest result.

Report it like a join: 300 records in, so many matched by rule, so many by review, so many unmatched.

The 45 new households are known only because the data is synthetic; in real work the unmatched pile mixes new people with missed matches, and the review queue is how you find out. The stretch counts 128 walk-ins with no accepted candidate.

After the match

  • Precedence: per field, the most trusted source that has a value; a blank never wins
  • Tie: two sources of equal trust that disagree go to the most recent, or to review
  • Lineage: every surviving value keeps its source and date
What goes wrong. Keeping one whole row, the first or the newest: an old phone survives a new one.

About two minutes. Lab 2.2 keeps the whole first registration of a repeated id, which is right for a join and would be wrong for a contact list. A master record (a golden record) is one row per real household, built from all the records a match put together. The rules are the network's own, written by the analyst and agreed with the owner of each field: Widad for the register. Trust follows how a value was obtained (verified, observed, reported) and how old it is, not which system is bigger.

Checkpoint

Which rule goes into the build?

A false match credits one family with another's parcels. On labelled pairs: name ≥ 70 accepts 309 with 86 false; name ≥ 95 accepts 117 with 4 false; name and phone accepts 172 with 0 false. Which do you automate?

Name ≥ 70: it finds the most matches
Name ≥ 95: 3.4% false is good enough
Name and phone, with the rest sent to review

Why. The costly error decides. Automate the rule that did not make it on labelled pairs, and spend human time on the records the rule leaves.

Answer: C. If someone argues for B, ask them to explain to the four families what happened. Then ask what would change the answer: if a false match were cheap (a mailing list, say), the name-only rule might be fine. The threshold follows from the cost, not from the score.

04
The same string, two days

03/07/2026 is 3 July at one branch and 7 March at another

  • 8 branches write 2026-07-03
  • 4 branches write day first: 03/07/2026
  • 2 branches, on donated software, write month first: 07/03/2026

36,002 of 91,403

From the Lab 2.4 run. FN-104 covered calendars (Hijri to Gregorian) and time zones; that is not repeated here. The problem today is more ordinary and more common: the same calendar written in different orders by different systems.

Where the evidence is

A layout belongs to the source: one unambiguous date settles the whole file

1 · Group by brancha branch uses one layout
→
2 · Look for a part above 12if the first part ever exceeds 12 it is the day
→
3 · Parse strictlywith that one format; a value that does not fit is an error
And then test the result. Every branch has handouts in every month. A branch read with the wrong layout would have none after day 12.

Two details. Raise an error when the evidence does not decide, rather than defaulting: a file of twelve days could be honestly ambiguous. And use an explicit format in pd.to_datetime; the convenient options (dayfirst, errors="coerce") are how wrong dates get in.

Day 2 · wrap-up

Three things to keep

No error is not correct

The wrong encoding, the wrong date order and a doubled household all run without a message.

Rows in = rows out + rows set aside

210,000 = 380 + 732 + 208,888. Each line has a reason.

Evidence lives in the source

The layout, the unit and the encoding are decided per file or per line, and measured before they are trusted.

Ask which of the four logs they would least like to defend to an assessor, and why. That is the one to rehearse before the capstone.
