Two different things

A repair fixes this file. A rule protects every file after it

  • Day 2 repaired what was found: encodings, keys, date layouts, units
  • The next extract arrives in three months, from the same 14 branches, with faults nobody has seen yet

The evidence of LO4

A rule suite that passes on the clean build and fails, readably, on a corrupted batch.

Ask who has opened a dataset, looked at df.describe() and called that validation. Looking is not a rule: it is not written down, it does not run next time, and it finds only what the person thought of on that day.

Quality dimensions

Each dimension becomes a kind of rule

DimensionThe questionA rule for the joined table
TypeIs it the kind of value the column holds?handout_date is written YYYY-MM-DD
CompletenessIs a required value there?household_key is never blank
ValidityIs it a value the dictionary allows?parcels between 1 and 3
UniquenessDoes a key identify one row?log_id never repeats
ConsistencyDo fields and sources agree?weight is 9 to 15 kg per parcel

Frameworks name and count the dimensions differently. The names matter less than this: every rule in your suite says which one it tests.

Session 1 covers the first four, which need one column each. Consistency needs two columns or two sources and is Session 2. Timeliness, which many frameworks add, belongs to the provenance record of Day 1 (the refresh date), not to a row rule.

Lab 4.1, steps 1 to 3

The data dictionary, written so that a program can check it

schema = pa.DataFrameSchema({
  "log_id": pa.Column(str, unique=True),
  "parcels": pa.Column(
      int, pa.Check.in_range(1, 3)),
  "weight_kg": pa.Column(
      float, pa.Check.in_range(5, 50),
      nullable=True),
  "handout_date": pa.Column(
      str, pa.Check.str_matches(ISO)),
}, strict=True)
schema.validate(df, lazy=True)
  • "Required: yes" in the dictionary is nullable=False, the default: the completeness rule
  • strict=True: a missing or an extra column fails
  • lazy=True: every rule runs, and all failures come back together
  • Dates stay text with a pattern: a date in another layout fails; it is not guessed

FN-104 (Lab 4.4) declared a Pandera schema on a daily file and reported failures lazily; treat the syntax as known. New here: the rules are written from the data dictionary of a joined table, each is named by its dimension, and each is shown to fail on a copy broken on purpose. The lab uses Pandera because the rules are plain Python next to the data frame. Great Expectations does the same job with a larger apparatus (suites, checkpoints, rendered documentation) and is the usual choice when a team shares the rules; name it and move on. Sources: Pandera documentation; Great Expectations documentation.

Testing the test

A suite that has never failed has never been tested

  • The suite passes on all 73,264 rows of the clean build. That proves little
  • A typing mistake in a pattern, or a range that is too wide, passes every build for ever
  • Break a copy on purpose, one fault per rule, and watch each rule fail
  • Decide in advance, per rule: does a failure stop the build, or warn?
What goes wrong. A suite is written after the cleaning, from the cleaned data, so that it passes. It then describes this file and protects nothing.

Stop or warn is the stretch of Lab 4.1. A repeated key or an unknown district corrupts every count: stop. An odd weight leaves the parcel count intact: warn, and count it in the log. The decision is the network's, and it is written down before the failure happens.

The limit of a rule

Valid is not the same as true

0
rows of the clean build fail "household_size between 1 and 20"
  • Lab 3.4: the audit found recorded sizes that differ from the verified size, more often above than below
  • Every one of those sizes is a whole number between 1 and 20
  • A rule tests what a value may be. Whether it is so needs a second measurement

Keep this slide short: it prevents the most common overclaim of a quality report, "the data passed validation", read by a manager as "the data is correct". The report of Session 4 lists self-reported size under limits for this reason.

What a column rule cannot see

B05 sent pounds. Most of its rows pass the range rule

278 · 377

  • A parcel weighs about 12 kg: about 26 in pounds

Lab 4.2, step 2

Two rules across fields

def not_per_parcel(df):
    ok = df.parcels.between(1, 3)
    per = df.weight_kg / df.parcels.where(ok)
    return df[per.notna()
              & ~per.between(9, 15)]

def before_registration(df):
    return df[date(df.handout_date)
              < date(df.registered_on)]
  • 9 to 15 kg per parcel: all 377 rows of B05, and no row of any other branch
  • Handout on or after registration: 30 rows in 12 branches. A household cannot collect before it exists: a wrong key or a wrong date
  • Each rule skips rows that another rule already reports, so one fault gives one line

The functions return the failing rows, not True or False: the rows are what the branch needs. Rows whose parcels are outside 1 to 3 are left to the validity rule; otherwise 40 rows with parcels of 30 would appear under two rules and the report would count one fault twice.

Lab 4.2, step 3

A branch cannot hand out more food than it received

B05 · received in the week
9,574 kg

20,005 kg
  • The logs say what went out; the donations source says what came in. No single table holds both
  • To compare them: the same unit, the same week, one row per branch. A small pipeline of its own
  • It catches a whole class of faults that leave every row plausible

Every other branch handed out less than it received that week. The rule is coarse: stock carried over from earlier weeks could make an honest branch fail, so in production it would compare over a longer window or include opening stock. Say so: a cross-source rule encodes an assumption about the world, and the assumption belongs in the rule's description.

Recap of FN-104, as a rule of the build

Reject the file, or set the rows aside?

Reject the file

The fault is in how the file was made: a wrong unit, a wrong layout, a missing column. Every row of B05 is suspect. Send it back.

Quarantine the rows

The fault is in single rows: a blank key, a date before registration. Load the rest; set these aside with a reason and count them in the log.

Either way the decision is made per rule, in advance, and the log shows it: rows in equal rows loaded plus rows set aside.

FN-104 (Lab 4.4) taught the choice on one daily file; do not teach it again, ask the room for the rule. What is new is that the decision is written per rule in the build of a joined table. This is the set-aside file of Day 2 again, now as policy. The third option, repairing silently inside the build, is the dangerous one: the reference build converts weights that are plainly in grams and records each change; ask the room whether a build should do that without telling anyone. It should tell: the change is in the log.

Completeness: no date is missing
Validity: the date is inside the quarter

Why. Each swapped date is a possible date. The fault shows only in a relation: the branch has no rows on 7 and 9 August, and about twice its usual rows on 8 July and 8 September.

Answer: D. Work one date through on the board: 08/07/2026 meant 7 August and is read as 8 July. 03
Before any technique

The safest field is the one that never entered the dataset

  • Lab 1.1 listed the fields the question needs. A name, a phone number and an ID number are not among them
  • They were needed for one step: matching the 300 walk-in records of Day 2
  • After that step they are dropped, and the dataset keeps a key that says "the same household" and nothing else

Minimise, then pseudonymise

First ask whether the field is needed at all. Only for what remains: how to replace the identifier so that tables still join.

Under the Personal Data Protection Law, personal data is any data that can lead to identifying a person, directly or indirectly, and collection is limited to what the purpose needs. The purpose here was written down on Day 1: service coverage analysis for the quarter. Sources: Personal Data Protection Law.

Recap of FN-106

Pseudonymised data is still personal data

Pseudonymised

Identifiers are replaced by codes. Linking back needs additional information, which is kept separately under its own controls. Somebody can still link back, so the data stays personal.

Anonymised

Nobody can link the data to a person any more, with any reasonable means. A much higher bar, and rarely reached by a table with one row per household.

The national guideline names generalisation and aggregation among the techniques: age bands in place of ages, a year in place of a date. Lab 4.3 uses both.

FN-106 (Session 3 of its first day) taught the two words, the keyed hash and quasi-identifiers on guardian and student records; keep this slide to two minutes. What is new here is measured: how fast a plain hash falls to enumeration, and how much generalisation it takes to bring re-linkage down on 37,333 households. The guideline defines pseudonymisation as transforming the primary identifiers into codes so that direct identification is not feasible without additional information, which is kept separately; it states that pseudonymised data is considered personal data. Sources: Personal Data Destruction, Anonymization and Pseudonymisation Guideline.

Lab 4.3, steps 1 and 2

"A hash cannot be reversed." Nobody needs to reverse it

5,000 of 5,000
people on a known list re-identified in a table of plain SHA-256 hashes
  • The same input gives the same hash, for everyone
  • List attack: hash the ID numbers you hold; join
  • Enumeration: an ID number has ten digits. Hash every possible one
  • The 2,000,000 numbers of the course range take seconds on a laptop; all ten-digit numbers take hours

From the Lab 4.3 run: two million candidates hashed in 6 to 12 seconds on one core, depending on the laptop, 37,333 of 37,333 households recovered; at that rate ten thousand million numbers take 8 to 17 hours, less on several cores. The ID numbers are synthetic, drawn from a range chosen so that the attack fits in the lab. Adding a fixed text to every number before hashing does not help once the text is known.

Lab 4.3, step 3

A keyed hash: without the key, neither attack starts

import hmac, hashlib, os

key = os.environ["GHILAL_KEY"].encode()

def pseudonym(s: str) -> str:
    return hmac.new(key, s.encode(),
        hashlib.sha256).hexdigest()[:16]
  • Stable and unique: the same household has the same pseudonym in every table, so joins still work
  • The key is the "additional information": kept separately, never committed, never sent
  • A list attack without the key: 0 of 5,000
  • A new key gives new pseudonyms: two recipients cannot join their tables to each other

HMAC is in the standard library; no package is needed. Where the key lives: an environment variable or a secrets store read at build time. The reference build falls back to a teaching key that is plainly labelled as not a secret, so that the course rebuilds without setup; a capstone repository must not do that. Sources: Python documentation, hmac; RFC 2104.

district, exact date, exact size

0.0%

Share of the 37,333 households whose combination of fields occurs exactly once.

  • "They live in D09, registered on 14 March 2024, seven of them": a neighbour needs no key

Uniqueness is a simple measure and a pessimistic one: it assumes the attacker knows all three fields. It is still the right first number, because it costs one group-by. A smallest group of 4 is not a guarantee of anything; with a sensitive field in the table (income) even a group of 4 can reveal that all four are below the line. The table stays personal data and travels under an agreement.
